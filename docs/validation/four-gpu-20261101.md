# 四卡 SmolVLM 验收与性能记录（2026-11-01）

源码为 `567ecf8`，模型为 SmolVLM-256M-Instruct BF16。机器可读结果见 [JSON](four-gpu-20261101.json)。
原始 JSON/JSONL、日志、GPU 遥测、源码快照保存在本机 `metrics/bitahub-takeover-20261031T163309Z/`，不随仓库提交。

## 验证结果

- 本机：106 项单元/集成测试、41 项启动器检查通过；3 项真实多卡用例因本机硬件不足跳过。
- 云端：拓扑 A、B 均完整执行并通过 16 项设备池测试，其中包含真实四卡 NCCL 用例；每种拓扑的 Gloo/NCCL 探针各 240 条测量样本，6 类真实模型输入、HTTP 非流式和 SSE 均对齐。
- 修复版本共 3420 条测量请求，包含 3240 条正式测量和 180 条并发冒烟；其中 2280 条 VPD 请求逐 Token 对齐单模型。HTTP 失败和 Token 不一致均为 0。
- 当前拓扑 B 的 NCCL 并发 1/2/4、Gloo 并发 2 四组正式基准全部通过，共 2160 条请求。实验前后 GPU UUID/PCI 地址一致，结束后无 GPU 计算进程，共享内存占用恢复为 0。

## 硬件、执行与负载

4×RTX 4090 24GB，驱动 580.105.08；Python 3.10、PyTorch 2.6.0+cu124、Transformers 4.51.3、NCCL 2.21.5。当前拓扑 B：V0/P1 在 NUMA 0、D2/D3 在 NUMA 1，1V+1P+2D，每卡一个 worker，`/dev/shm` 为 10GiB。
CUDA peer access 的 12 个有向卡对均为 false；调试探针的通道日志明确显示 `via SHM/direct/direct`。这是主机共享内存路径，不能称为直接 CUDA P2P、NVLink、RDMA 或全程零拷贝。
每请求两张固定随机种子的 64×64 合成图片，统一预处理到 512×512；四种问题轮换，prompt 为 148～150 Token，固定 greedy 生成 8 Token。视觉 LRU 为每 V 16MiB，接纳上限为 4。性能组关闭完整载荷 SHA256，身份、形状、预算和 ACK 检查仍保留；正确性验收使用开启校验的路径。
每配置、每模式、每场景 3 轮×20 请求；每场景相同的 5 条预热不计入测量。三模式为单模型、VPD 无缓存、VPD 有缓存，模式顺序按轮次轮转。吞吐为有效输出 Token / 整组请求墙钟时间，模型启动不计入稳态延迟。

## 同一拓扑、同一四卡布局的并发对照

下表为 NCCL、冷图、关闭视觉缓存，比较的是同版 VPD 程序的客户端并发。

| 客户端并发 | 有效输出 Token/s | TTFT P50/ms | E2E P50/ms | 路由等待 P50/ms | 同时解码副本峰值 |
|---:|---:|---:|---:|---:|---:|
| 1 | 23.9 | 144.4 | 342.9 | 0.2 | 1 |
| 2 | 44.9 | 145.6 | 346.9 | 0.2 | 2 |
| 4 | 46.4 | 456.0 | 651.6 | 332.2 | 2 |

并发 1→2 时吞吐提高 87.5%；并发 2→4 再提高 3.5%，但路由等待 P50 增至 332.2ms、TTFT P50 增至 456.0ms。
两个 D 的解码区间确实重叠，同一 D 的解码区间没有自重叠。路由提前预留 D，最多两条活动路由，其余请求在主进程 FIFO 等待；增加客户端并发不会增加 D 副本数。

这些比例使用相同四卡布局和同版程序，表示不同闭环客户端并发下的容量变化；不是旧串行实现与新版路由的代码消融，也不是单卡单模型与四卡 VPD 的等预算扩容收益。

## 通信探针与真实服务的区别

当前拓扑的 8MiB BF16 P→D 完整交接探针，每条边 3 次预热、10 次测量：

| 边 | Gloo P50/ms | NCCL P50/ms | 降低比例 |
|---|---:|---:|---:|
| P1→D2 | 9.17 | 0.70 | 92.4% |
| P1→D3 | 9.30 | 0.76 | 91.9% |

探针包含发送端 staging、数据传输、接收端 staging/逐元素校验和 Gloo ACK；不等于裸链路带宽，也不包含真实 KV 打包和全部应用元数据处理。
相同并发 2、关闭视觉缓存的真实服务对照：

| 负载 | Gloo Token/s | NCCL Token/s | Gloo E2E P50/ms | NCCL E2E P50/ms |
|---|---:|---:|---:|---:|
| 热图 | 45.3 | 44.8 | 340.2 | 346.4 |
| 冷图 | 44.4 | 44.9 | 346.6 | 346.9 |
| 混合复用 | 44.1 | 43.8 | 348.2 | 349.3 |

本次小模型短输出负载没有显示 NCCL 在所有场景中一致的端到端优势，不能从大载荷探针推导服务同幅加速。首 Token 由 P 在 KV 交接前报告，分析 KV 通信还需看后端首/第二 Token 间隔、TBT 和 E2E，SSE 分块间隔不等同于 Token 间隔。

## 正确性修复与失败证据

初版 `0886b07` 在混合复用第 20 条请求（图片种子 `[0,2019]`）上三轮均发生 Token 不一致；540 条请求的 HTTP 均成功。失败记录未删除，也未纳入修复版本通过数。
直接 CUDA 诊断确认：部分命中将 encoder batch 从双图缩为单图后，特征有 33554 个值不同，最大绝对差 0.75；用重复缺失图片补齐双图 batch 后，该样例特征逐元素相等，生成 Token 恢复一致。
提交 `567ecf8` 将缓存条目按请求图数隔离，并保持部分命中、重复图片去重后的原 encoder batch 大小，仅保留缺失结果；新增实际 encoder 槽位与补齐成本计数及三项回归。
PyTorch 不保证批量计算与逐切片计算位级相同，见 [数值精度文档](https://docs.pytorch.org/docs/2.6/notes/numerical_accuracy.html#batched-computations-or-slice-computations)。本修复的保证范围以本轮硬件、依赖和逐 Token 对照为准，不外推跨平台位级一致性。

## 适用范围

- GPU 频率与 CPU 亲和性未锁定，Gloo/NCCL 实验块未全局随机交错；很小差异仅作描述，不宣称统计显著。
- 单模型占一张 GPU、VPD 占四张 GPU；不据此声称等资源成本降低或线性扩容。
- 这是合成图片复用负载和固定短输出；不代表生产流量、长输出或生产 P99 SLO。
- 当前没有连续批处理、同 worker 计算通信 stream 重叠、TP、多机或 RDMA。
