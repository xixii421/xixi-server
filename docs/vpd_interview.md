先读 [简历文案](resume_project2.md) 和 [当前架构](architecture.md)，再结合源码讲解。
历史单卡 [实验报告](vpd_benchmark.md) 需按当时源码与负载解释，不能移作当前三卡结果。
简历中的指标必须连同负载条件解释；不要把阶段计时、客户端延迟和生产 SLO 混用。

## 计算链路

这个后端采用真实 SmolVLM/Idefics3 视觉语言模型。V 进程保留视觉 Transformer 和投影
Connector；P、D 保留语言 Transformer 和 LM Head。先由 V 产出语言隐藏维度的视觉 Token，
再由 P 替换输入序列中的图像占位符，执行 Prefill，生成首 Token 和历史 KV。
D 在自己分配的缓存中恢复历史状态，每一步只输入上一个生成 Token。

这是图像特征插入语言序列的架构。视觉信息已经进入 Self-Attention KV，D 不需要重复编码图像。
Cross-Attention 模型可能还需要视觉侧状态，此项目没有把这类适配写成已完成。

源码入口：`vpd_local.load_stage`、`encode_vision`、`language_forward`、`vpd_worker`。

## 交接协议与故障边界

主进程与 worker 用 Queue 传请求/事件，worker 间元数据和 ACK 用 Gloo；
载荷通道可选 CPU/Gloo 或 CUDA/NCCL。HTTP 通过 prepare/run_prepared 避免重复解码图片。
V/P/D 分别校验 UUID、通道序号、prompt 摘要、有序图片上下文、模型配置/来源、shape、dtype
与可选的内容 SHA-256。接收方验证完毕后发送 ACK，发送方才释放相应源状态。
Gloo 模式先经 CPU 中转，再复制到接收端 GPU；NCCL 模式在各阶段 GPU 上收发张量。
完整 SHA256 校验和 CPU 视觉缓存仍可能产生 CPU 镜像/搬运，不能统称零拷贝。

取消或超时后，如果不能确认在途操作是否结束，不能只释放张量然后复用通信通道。
当前采取 fail-stop：停止并回收整个三进程组，要求重启。它牺牲可用性来保持状态和内存安全，
尚未实现在线重建通信组。预处理拒绝发生在传输前，可以安全继续下一请求。

源码入口：`feature_header`、`receive_features`、`vpd_transport.send_kv`、`receive_kv`、`LocalPD.close`。

## 视觉特征复用

视觉编码器与 Connector 的输出不依赖后续文本问题，因此同图多轮提问可以复用视觉特征。
缓存不复用文本 KV，改变问题仍会执行新的 Prefill。

Key 包含原始图片字节摘要、模型配置/来源/精度的签名及固定预处理命名空间。
图片按字节寻址：不同编码的同一视觉内容可能不命中，但不会因文件名相同而误复用。
模型在 worker 生命周期内不可热更新；修改权重或预处理后必须整组重启，清空旧缓存。
签名不是整个权重文件的内容校验，不应宣称实现了任意在线模型版本管理。

部分命中时只编码缺失的图片，通过 Key 恢复原始图片顺序。
开启复用时，同一请求中的重复未命中图片只编码一次。预处理仍执行，命中并不意味着整个视觉阶段耗时为零。

源码入口：`vision_cache.VisionFeatureCache`、`vpd_local.encode_cached`。

## 字节预算与所有权

LRU 的单位是实际张量 payload 字节。插入时复制、读取时复制，避免请求修改共享缓存，
也避免一个小 tensor view 保留整个大 batch 的底层存储。

16MiB 指 CPU resident cache 上限；active handoff、模型权重、激活、KV、CUDA context 和临时副本另计。
这不是“所有进程显存最多 16MiB”。输入图片数量、原始字节、像素数、feature payload、生成长度
和 KV payload 还有各自的上限；HTTP 接纳数量为 2，生成请求串行执行。

## 实验归因

对照为持久单体模型、相同三阶段但关闭缓存、相同三阶段启用缓存。
三个配置使用同一预处理、正常 KV、greedy、图像与输出长度。模型加载和预热不计入正式测量。
缓存收益优先相对“同一三阶段无缓存”说明，不能把它归因于 PD 本身。

正式负载为合成图片复用模式：重复图片、全新图片、混合复用；每配置每场景 3 轮、每轮 20 请求。
轮换三种配置的先后顺序，保留每轮与全部原始请求，GPU 不锁频，因此结果限于这台笔记本。
吞吐按测量 cohort 的墙钟时间计算；请求 fixture 构建和日志写入在计时外。

单体基线是常驻完整模型，正常使用 KV。不能拿每次加载模型、关闭 KV 或重复重算全上下文的版本
作为主要基线，把这些额外成本算成优化收益。

## 环回代理排查

最初部分请求客户端耗时数秒，引擎内部只有几百毫秒。把二者对齐后，发现本机环境没有为
127.0.0.1 绕过代理。客户端现对环回地址显式使用无代理 opener，远程地址仍使用正常代理策略。
增加了“错误代理且 NO_PROXY 为空时，本机请求仍能成功”的回归测试。

旧实验没有删除；正式结论使用修正后的完整新实验。不能把受扰数据中慢请求删掉再宣称稳定收益。

源码入口：`stream_benchmark.open_endpoint`、`is_loopback`，以及 `test_stream_benchmark.py`。

## 指标含义

- 客户端 TTFT：从请求开始到首个非空 SSE 内容，含 HTTP、排队、预处理及模型相关等待。
- 后端 TTFT/TBT：worker 的逐 Token 就绪时间，不能替代客户端体验。
- SSE 内容可能一次包含多个 Token。分块间隔不是精确逐 Token TBT。
- 60 个请求的 P95/P99 只能做描述，不能由此保证生产服务 SLO。
- 冷图无命中收益，应同时报告缓存查找、复制及存储的代价；混合场景的长尾不能省略。
- 所测请求逐 Token 对齐不等同于证明所有输入 logits 相等或任务准确率完全不变。

## 建议亲自完成的练习

1. 从 HTTP handler 跟一次单图请求，指出两次张量交接和 ACK 的具体位置。
2. 用同一图片问两个不同问题，解释哪些计算被复用，哪些仍执行。
3. 将缓存预算调到只能容纳一张图，观察 resident bytes、eviction、hit/miss 和输出。
4. 交换两张图片的顺序，比较 feature digest、上下文摘要和生成结果。
5. 解释客户端长尾远大于引擎耗时时，应该检查哪些边界。
6. 从 JSONL 手工算出一个场景的 TTFT 中位数和吞吐，核对报告。
7. 解释为什么单卡回环验证不能支持跨 GPU NCCL 性能或分布式扩展性结论。
8. 说明如果要支持连续批处理或跨请求流水线并发，需要重新设计哪些排队和通信次序。
